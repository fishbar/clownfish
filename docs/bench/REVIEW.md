# 明早 review 用的总结

一句话：**质量上和 Claude Code 全平（4 轮、12 道题，双方每一项都满分），速度快 1.3–4.8 倍；这一晚真正抓出来的 bug，绝大多数在我的评测台上，不在两个智能体身上。**

## 二、比赛：同模型、同题、比 harness

两边都指向同一个 GLM 代理（Claude Code 用 `--model sonnet` 映射到同一档），Claude Code 侧显式开子代理并隔离配置目录——不补这一句等于让对手空着手上场。评分只认**智能体没见过的隐藏测试**。

| 轮次 | 题集 | clownfish | claude-code | 用时 |
|---|---|---|---|---|
| 1 | phase1（5 题：并发竞态 / 性能热点 / 巨模块拆分 / 运维排障 / semver 规格） | 19/19 | 19/19 | 408s vs 1326s（3.3×） |
| 2 | phase2（5 题，对标 SWE-bench / Terminal-Bench / Aider Polyglot / SEC-bench） | 17/17 | 17/17 | 245s vs 1169s（4.8×） |
| 3 | phase3（13 模块回调→Promise 迁移） | 5/5 | 5/5 | 153s vs 206s（1.3×） |
| 4 | phase3（迁移复跑 + 8 接口横切演进） | 9/9 | 9/9 | 362s vs 606s（1.7×） |

**结论一：这批题对当前模型已经触顶。** 前两套双方满分，继续刷轮次没有信息量，所以第三套改出"宽"题（13 个模块、8 个接口）。触顶本身就是结论。

**结论二：区分度在效率上，而且不只是时间。** clownfish 每题 4–17 次工具调用收敛；Claude Code 慢 1.3–4.8 倍。

| 四轮合计 | clownfish | claude-code |
|---|---|---|
| 总 token | **1.32M** | 6.87M（**5.2×**） |
| 输出 token | 49k | 222k |
| 缓存命中率 | 83.5% | 94.7% |

分数完全一样的前提下，**clownfish 少烧 5.2 倍 token**。Claude Code 的缓存命中率更高（每题 42 个 turn，固定前缀被反复命中），但它推过模型的上下文总量大得多——命中率高不等于省。两边的 `cacheWrite` 都是 0，说明缓存是 GLM 代理侧的隐式前缀缓存，不是我们能调的参数；命中率差异主要来自会话形状（turn 数、子代理各自独立的前缀），不是配置问题。

clownfish 第 2 轮命中率只有 72.6%，明显低于其它轮——那一轮任务最碎（5 道小题、每题 4–7 次工具调用），会话太短，首个请求的未命中占比自然被放大。

**结论三：改进有效但幅度小。** 第 3→4 轮之间改了计划契约（委派挂到计划步骤 + 重写保台账），计划卫生度从"委派另起一条、原步骤永远 pending"变成 4 步里 3 步收尾、1 步遗留。质量分本来就满，改进只体现在这类可观测的过程指标上。

## 三、反思能力的实证

拿一段合成会话（用户三次要求中文、一次指出"没跑 typecheck 就说完成"、一次说明 dev server 要用 `make dev`）跑真实模型：

- `[preference] always-reply-in-chinese` — 必须用中文回复
- `[lesson] run-make-typecheck-after-code-changes` — 改完代码必须先跑 typecheck 再汇报（带根因）
- `[preference] use-make-dev-not-npm-run` — 本仓库用 `make dev`

而基准会话里 `memory/` 是空的——**这是正确行为**：那些会话没有用户纠正，提示词明确要求"多数会话应当返回空"。

## 三点五、那一分失败的复盘与改进实验

**先修正结论：这不是能力差距，是尾部事件。** 把 `flaky-ci` 在各种配置下一共跑了 **33 次，失败 2 次（约 6%）**，而且两次栽在**不同的缺陷**上：round 5 是时钟粒度那个（`>=` + `Date.now()`），另一次是根本没消掉模块级共享状态。单次跑分区分不了"harness 更强"和"这次运气好"。

**失败机制（精确版）：验证手段看不见它被要求修的那个缺陷。** 题目给的测试用 `ttlMs: 1000`，而缺陷只在 `ttlMs` 极小时才踩到毫秒跳变——**把既有套件重跑一万遍也发现不了**。round 2 那次它整文件重写并换成 `performance.now()`（单调时钟，根治）；round 5 那次它做了个定点 `edit`，把 `>` 改成 `>=` 还留着 `Date.now()`，然后跑了 5 遍套件看到绿就收工。两次都"验证过了"，但验证的是"给的测试通过"，不是"点名的缺陷消失"。

**做了四组实验**（每组重复跑同一题，看**过程指标**而不只看罕见的失败——过程指标的统计功效高得多）：

| 变体 | n | 满分率 | 为缺陷造探针 | 用 qa 独立验证 | 平均 token/次 | 平均耗时 |
|---|---|---|---|---|---|---|
| 基线 | 6 | 6/6 | **0/6** | **0/6** | 49k | 42s |
| 规则写进 `coding.md` | 12 | 11/12 | 1/12 | 0/12 | 81k | 72s |
| 规则改写进 `system.md` | 12 | 12/12 | **3/12** | 0/12 | 57k | 45s |
| 再开 `thinking=medium` | 1 | 1/1 | **1/1** | **1/1** | 281k | 339s |

三个发现：

1. **规则放错文件等于没放。** 这类小题 orchestrator 全程自己做、从不委派，所以写进 `coding.md`/`qa.md` 的规则**根本不会被加载**。挪进 `system.md` 后，"为缺陷造针对性探针"从 0/6 变成 3/12。
2. **`qa` 是死的：29 次运行里 0 次被调用。** 原因是提示词自相矛盾——"委派要花一整个 agent run，小活自己干"这条压过了"属性类目标要交给 qa 验证"。光加一句话推不动它。
3. **扩展思考是唯一真正产生预期行为的杠杆，但贵 7 倍。** 开 `thinking=medium` 那次，它自己写了 `probe/coarse-clock-probe.mjs`、改前改后各跑一遍、套件连跑 50/60 次，**并且第一次委派给了 `qa`**——正是设计时想要的行为。代价：339s / 281k token / ¥1.69，约为不开时的 7 倍。

## 三点六、提示词压缩（读入内存时去掉给人读的格式）

做了，也测了：`agent/prompt-compact.ts`，在 `assembleSystemPrompt` 这个唯一出口生效（agent 提示词 + 框架生成的工具区块 + 技能索引一并覆盖）。围栏代码块、行内代码、缩进样例逐字节保留（里面有 `{cwd}` 这类占位符和 JSON 形状）。**只去排版，不改写文字**，`make e2e` 断言每个内置提示词压缩前后的字母数字完全一致。

**结论：能省，但对当前提示词几乎没用。**

| | 压缩前 → 后 | 节省 |
|---|---|---|
| 首个请求的提示词 token（实测，n=12 全为常数） | 5,255 → 5,215 | **-0.76%** |
| 完整组装的系统提示词（字符） | 11,897 → 11,800 | -0.8% |
| 框架生成的工具区块 | 5,565 → 5,471 | -1.7% |
| 对照：重格式风格的提示词 | 353 → 288 | **-18.4%** |

原因很直接：**我写的提示词里本来就几乎没有给人读的格式**（`system.md` 全文只有 1 行含 `**`），都是散文段落和 `- ` 列表。真正值钱的场景是**别人在设置页里粘进一份带表格、标题、加粗的文档**——那时能省 ~18%。

折算成钱：每次运行约省 280 token（40 token × 约 7 个请求），≈ **¥0.0005/次**；五轮基准全部加起来省不到 ¥0.03。

**行为没有退化**：压缩开/关各跑 12 次，满分率都是 12/12，平均工具调用都是 6.8。"为缺陷造探针"是 5/12 vs 3/12——差 2 次在 n=12 下是噪声，不能当成改进。默认开启（免费、保义、且正好覆盖设置页那个使用场景），`CLOWNFISH_COMPACT_PROMPTS=0` 可关。

## 三点七、三个改进的落地与实测

**① 按任务选择性开 thinking。** `run_agent` 新增 `thinking` 参数（会话默认来自 `CLOWNFISH_THINKING` / 项目配置，仍是 `off`）。实测 `medium`：它自己写了 `probe/coarse-clock-probe.mjs`、改前改后各跑一遍、套件连跑 50/60 次，**并且第一次主动委派给 qa** —— 正是设计想要的行为，代价约 7 倍（339s / 281k token）。所以做成**每次委派可选**，不是全局开关。

**② qa 从"可选委派"变成框架强制的第二遍。** 委派**改动了工作区**之后，`run_agent` 自己起一个 qa，把原任务+实现者的报告交给它，读它末尾的 `VERDICT: PASS|FAIL`。`CLOWNFISH_VERIFY=off|auto|always`，默认 `auto`（只在真的改了东西时付这笔钱）。

**实测的诚实结论：机制生效了，判断不一定对。** 第一次真实触发时（`sub2-qa.jsonl` —— qa 在整个研究里第一次被调用），它认真写了探针、做了边界分析，然后给出 **PASS**，而我的隐藏测试判它 0/3。它把自己探针测到的命中解释成"取时间戳的时序假象"。**独立验证 ≠ 正确验证**，这条要记住。

**③ 失败即回滚重试。** 用强制 FAIL 的 qa 覆盖端到端验过：`sub1-coding` → `sub2-qa`(FAIL) → **回滚** → `sub3-coding`(重试) → `sub4-qa`(再 FAIL) → 返回"验证失败且重试预算耗尽"给编排者 —— 编排者**没有盲信**，自己读代码做了定点修复，最终 5/5。

**回滚现在覆盖 bash 了**（按你的要求）：检查点从"只存 write/edit 的文件预映像"改成**有序动作日志**，bash 调用前抓整树快照（git 仓库用 `git stash create` + untracked 列表，非 git 的小工作区用整树副本），回滚**逆序回放**，遇到无法还原的动作**就地停下并说明**，绝不半回滚。19 项断言覆盖 git/copy 两种模式下的"bash 改写/删除/新建"，已并入 `make e2e`（现在 166 项）。

**并行危险会提醒到用户**：回滚前后各发一条 `notice` 帧（不是 `error` —— 那会顺带 reject 掉挂起的 compact/mode 应答），UI 上能看到；同一棵树里还有其它委派在跑时**自动跳过回滚**并说明原因，改为向前重试。

## 四、我自己踩的坑（完整列表见 CASES.md）

一共 14 条，其中最贵的一类重复犯了四次：**用结构去检查实现，而不是用行为**。

- `node --test test/`（目录形式）在 Node 24 下会把目录当模块 → 把两边**都解决了的题**判成失败。
- Node 24 默认 spec reporter 而非 TAP → 隐藏测试计数恒为 0，**所有正确解被判零分**。
- 隐藏测试断言了参考实现根本没有的行为（`An Ode to Joy`，可小词表里没有 `to`）。
- 钦定"必须抛异常"，而"安全地容纳"同样正确 → 冤枉 clownfish 一分。
- 自己写的隐藏测试内部矛盾（`max:5` 的缓存写 20 条还要求全部可读）。
- `api-versioning` 查"目录里必须正好 8 个文件、每个文件都要出现 limit"→ clownfish 把分页抽成共享模块复用（**更好的设计**），行为 8/8 全过却被判两项失败。
- `make bench-dry` 默认写进 `round1`，把第一轮真实产物覆盖了 → 我没有伪造数据，用修好的验证器**重跑了整轮**，并把基线固定到 `round 0` + 加了拒绝覆盖真实轮次的护栏。
- `pkill -f "tsx server/index.ts"` 顺手杀掉了基准自己的服务 → 那一轮作废重跑。

现在每道题都声明 `expectDry`（空跑应得几分），`make bench-dry` 逐题核对，低了说明种子坏了、高了说明白送分，不符直接非零退出。

## 五、需要你拍板

1. **要不要让 clownfish 跨轮次继承记忆。** 现在每轮独立 dataDir，测的是"纯 harness"；打开继承能测"自我改进"，但会把提示词改进和记忆效应混在一起。
2. **题目要不要再上一档。** 当前难度对这个模型偏简单，下一档得是更长时程的（真实开源仓库的 issue、跨天的迭代）。
3. **计划里"自己做的步骤"没人收尾**（第 4 轮还剩 1 步 pending）。提示词已经写了要求，如果还想更硬，可以在回合结束时注入一条提醒——那会改动对话内容，所以先问你。
4. **要不要把"每题 token 预算"也纳入评分。** 现在分数只看隐藏测试，效率是旁证；如果把 token 预算做成硬约束，题目就能同时考"做得对"和"做得省"。
5. **`~/.clownfish/settings.json` 里现在写着 GLM 测试 token**（从 `~/.claude/settings.json.glm` 取的，权限 600，已 gitignore）。要不要保留。
